## Stage 1 design problems corrected in Stage 2

Stage 1 files stay unchanged. These are cases where following the Stage 1 design literally would have produced incorrect, unsafe or unimplementable behavior; each correction keeps the feature's user value and is covered by tests.

Format: Original Stage 1 design → Identified problem → Corrected Stage 2 design → Technical justification → Affected features/classes/UML.

| Original Stage 1 design | Identified problem | Corrected Stage 2 design | Technical justification | Affected |
| --- | --- | --- | --- | --- |
| `SessionService.transition(id, event)` reachable from GUI/CLI for every `SessionEvent` | §4.5 says a valid approved plan moves Draft → Planned and a saved review moves Completed → Reviewed; a free event choice lets the user claim either without the record | `recordEvent` + `MANUAL_EVENTS` (SHOOT_COMPLETED only); the other events come only from F10 approval and F11 save; State guards unchanged | A workflow event must be produced by the workflow that creates its evidence | F01/F10/F11; `SessionService`, `SessionPane`, `SessionCommands`; SD01 (`CliErrorBoundaryTest`, `SessionGuiTest`) |
| Facade `createSession(title, date)` only | F01 input requires optional location and notes; the Stage 1 table itself records "no exposed mutation route" | `create(title, date, location, notes)`, `update`, `delete`, `search(query, status, date)`; Stage 1 signature kept | Fulfils the stated F01/UC01 inputs | F01; `SessionService`, `SessionForm`; class diagram, SD01 |
| F02 `select`/`save`/`dismiss` with no route; target session unspecified | Stage 1 table: "lack a Facade route and are not sequenced"; creating a session first and attaching the idea second leaves an empty session when the second step fails | `discover(request)`/`discovery()`; `selectInNewSession`/`saveInNewSession` check everything first and insert session + idea in one atomic write | All-or-nothing persistence (UC01 E1, UC02 A2) | F01/F02; `DiscoveryService`, `SessionService.draft`; SD01 (`DiscoveryHandoffTest`) |
| F02 output "estimated time and travel" | No routing or traffic source exists in the design; an LLM estimate would be an unverified figure (§1.4 keeps measurements deterministic) | Straight-line distance from gazetteer points, labelled; travel time always stated as unknown | Only verifiable values are presented as facts | F02; `FeasibilityValidator`, `ActivitySuggestion` |
| Four agent tools registered (`calculation`, `environment`, `gearMatching`, `specification`) | `EnvironmentTool` needs coordinates, which must never go to Gemini; `SpecificationTool` would send model-chosen strings to external catalogues; `GearMatchingTool` repeats F07 candidates already given to F10 as labelled offers | Only `calculation` is registered; `ToolRegistry.register` refuses tools without an input schema; the three classes remain unregistered | Location privacy, no model-driven network egress, no duplicate evidence | F10; `ApplicationBootstrap`, `ToolRegistry`; class diagram, SD04 (`HistoryMemoryTest`, `BootstrapTest`) |
| `ModelReply.toolCalls` (native function calling) | Every task already uses `responseJsonSchema` structured output; native function calls would be a second, separately parsed reply channel, and nothing in that form limits a call to the task's allowlist | Structured envelope (`step` = `tool` or `final`) whose schema enumerates only the permitted tools; bounded loop (`runWithTools`, 8 steps, repeat/failure limits) | One schema-validated channel; unpermitted tools cannot be expressed | F10; `PhotoPilotAgent`, `GeminiAdapter`; SD04 (`AgentToolLoopTest`) |
| `GearMatchingService.setRanking(strategy)` before matching | Setting a per-request GUI/CLI choice on the shared service would silently apply one request's preference to later requests from other panes and windows | Per-request `analyze(..., strategyName, ...)`; `setRanking` only sets the default | No shared mutable state per request | F07; `GearMatchingService`, `AiAssistedRanking`; class diagram |
| `PlanEditor.preview(base, change)` with one command | One natural-language request ("lighter and earlier") can affect several sections; separate previews could approve an inconsistent intermediate plan | `preview(base, List<PlanCommand>)` applies all commands to one copy and validates the result once | Atomic revision, validated as a whole | F10/UC11; `PlanEditor`, commands; SD04 (`PlanValidatorTest`) |
| F09 assessment returned to F10 with no persistence | Persisting forecasts would show stale weather as current evidence; not persisting loses it at restart | Kept in memory with freshness checks; after a restart F06/F10 state that no current assessment exists and ask to reassess | Freshness over convenience; no new schema for volatile data | F06/F09/F10; `PlanningService`, `CapabilityNeedForm` (`F10WorkflowTest`) |
| `DeviceLocationProvider` for current location | Desktop Java has no portable location API (the design already marked it deferred) | No provider; `LocationService.current` asks for consent, then reports unsupported; manual/approximate places everywhere | Honest capability report; manual location satisfies UC01/UC02/UC09 A1 | F01/F02/F09; `LocationService` (`LocationServiceTest`) |
| `AgentContext.history: List<PhotographySession>` | Whole sessions (locations, notes, ids) in the model context would leak private data | Sessions stay in memory; only bounded summaries without locations or ids go into the evidence JSON | Data minimisation | F10/F11; `HistoryRetriever`, `GeminiAdapter` (`HistoryMemoryTest`) |
| UC14 "missing specifications → unverified" applied to empty values only | Only blank or `unknown` was treated as missing; text such as `n/a` or `-` counted as a recorded mount, so two identical placeholders looked compatible | Shared `SpecificationValues` policy for every compatibility rule and the F06 report | Unknown is never compatible | F06/F07/F10; `CompatibilityValidator`, `GearCapabilityService` (`UnknownSpecificationTest`) |

## Design patterns

The five Stage 1 patterns (Facade, Strategy, Adapter, Command, State) have runtime roles; see the [Stage 2 README](../README.md#architecture-and-patterns). Two more are used where they fit and should appear in the Stage 2 UML: **Decorator** (`LanguageAwareLLMClient` wraps `LLMClient`) and **Template Method** (`AiAssistedRanking` for both ranking strategies).

Kept deliberately (evidence in source):

- `SanitizedImage` stays in `ui.privacy`: its constructors are package-private, so only `ImagePrivacyBoundary` can create an approved image, although `service` and `agent` read it.
- `ShootPlan` stays in `command`: its mutators are package-private, so only the plan commands can change a revision copy.
- GUI/CLI reach services through Facade accessors (`sessions()`, `planning()`, …), as in the Stage 1 design. Facade dependencies are final.
- Stage 1 members without production callers stay for traceability and tests: `ModelReply.toolCalls`/`clarificationQuestions`, `PlanEditor.applyApproved`, `RequirementService.deriveProfile`, `GearMatchingService.setRanking`, `HistoryRetriever.retrieve`, `InventoryService.duplicates`, `EquipmentSpecificationProvider.lookup`, `PhotoPilotGUI.draftInput`/`privacy`. Each appears in the Stage 1 class diagram.
- One worker queue per GUI window: AI requests never run on the JavaFX thread (`UiOperationsThreadingTest`), but later work of the same window waits behind them, in order, and counts as busy for safe profile switching. There is no cancel action yet.
